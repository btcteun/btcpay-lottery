# Lightning Lottery

A provably fair lottery for local events, powered by BTCPay Server and Lightning.
No names, no email, no KYC — the participant's wallet is the proof.

## How it works

1. People pick a number of tickets on the page and pay a BTCPay invoice.
   After payment BTCPay redirects them back and the page shows their ticket
   numbers. Sales at a BTCPay POS on the same store are picked up as well.
2. A public page shows the tickets sold in real time. Each invoice gets a
   random 7-character ticket ID (A-Z, a-z, 0-9, case-sensitive) and a 5-digit verification code,
   both generated by the app. `ID-code` (e.g. `Kq7zR2x-48213`) is the BTCPay
   order ID and the invoice memo, so buyers see it in their wallet. Only the
   ticket ID is public; only a hash of the code is stored. Several tickets on
   one invoice are numbered `ID-1`, `ID-2`, …
3. At closing time the ticket list is frozen and its SHA-256 is published
   before the drawing block exists.
4. The first Bitcoin block mined after closing time picks the winners.
   For prize *n*: `SHA256(blockhash + "," + sorted ticket list + "," + n) mod remaining tickets`.
   The winning ticket leaves the pool, the buyer's other tickets stay in.
   `PRIZE_COUNT` sets how many prizes are drawn. `BACKUP_COUNT` extra rounds
   draw stand-in tickets, in order, for winners who have already left: the
   organizer marks the prize as forfeited and it passes to the next unused
   backup (the public page strikes the old ticket through). Backups are only
   visible on the organizer page. Anyone can verify the prize rounds with any node.
6. Claims are handled on `/organizer` (enter `ADMIN_TOKEN` there); `/` is safe
   to put on a big screen.
5. The winner claims the prize in person by showing the payment memo in
   their wallet: `ticket ID-verification code`. The organizer types the
   5-digit code in and the server answers match / no match. Only a hash of
   the code is stored and it is never published. If the store's Lightning
   backend returns preimages, the preimage is accepted as proof as well.

## Run it

```bash
cp .env.example .env                        # fill in BTCPay creds, times, secrets
mkdir -p data && chown 10001:10001 data     # container runs as uid 10001
docker compose up -d --build
docker compose logs -f
```

The page is on `http://127.0.0.1:8000`. Put Caddy or nginx with HTTPS in front
before exposing it to the public.

State is written to `./data/<DATA_FILENAME>`. Change the filename in `.env`
for each event; old files stay as an audit trail.

## Before going live

- Confirm where your BTCPay version puts the Lightning preimage in the
  `payment-methods` API response and adjust `fetch_invoice_preimage()` in
  `app.py` if needed.
- Confirm BTCPay's public receipt page does not expose the preimage.
- Set `PUBLIC_URL` to the HTTPS address of this page (used for the redirect).
- Give the API key `canviewinvoices` and `cancreateinvoice` permissions.
- Set `TICKET_PRICE_SATS` to exactly what your POS charges. Tickets must be
  priced in SATS or BTC.
- Generate `ADMIN_TOKEN` with
  `python3 -c 'import secrets;print(secrets.token_hex(32))'`.
- Check whether a lottery needs a permit in your jurisdiction.

## Trust model

- Buyers can verify the draw independently.
- The organizer holds the BTCPay API key and can read every order ID (with
  the verification code) and preimage, so the scheme proves a buyer paid; it
  does not stop a dishonest organizer.
- The verification code is a shared secret, not a cryptographic proof:
  anyone who sees the buyer's wallet memo could learn it. Fine for a small
  in-person event. Backends like LNDhub do not return preimages at all.
  Publishing the commitment hash somewhere immutable (print, Nostr) keeps you honest.
- Block timestamps are set by miners and can drift. For stricter fairness,
  announce a fixed block height instead of a closing time.
- Point `BLOCK_API` at your own node to remove the mempool.space dependency.
